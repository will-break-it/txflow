# Data Model: `txflow` file formats

Formats for the artefacts in [`spec.md`](./spec.md): experiment spec, graph IR,
manifest, schedule and results, plus the chain context materialise reads. All
human-edited files are YAML; machine-written files are JSON or JSON Lines. Field names
are `snake_case`. Every file carries `version: 0` until the format is declared stable.

## 1. References and names

| Form | Meaning |
|---|---|
| `wa` | a **source**: an abstract funding output declared in `sources` |
| `a1.0` | output 0 of transaction `a1` |
| `chains/a1` | transaction `a1` emitted by pattern instance `chains` |
| `chains/a1.0` | output 0 of that transaction |

Transaction, source, wallet, validator, policy and pattern-instance names match
`[a-z][a-z0-9_]*`. A pattern instance namespaces every name it emits with `<id>/` when
it has no `count`, and with `<id>_<k>/` (k = 0, 1, …) when `count` is written, whatever
its value, so scaling `count` through a param does not rename anything.
Labels, target names and the experiment name are free strings; none of them is written
into transaction metadata (§4). A reference that does not resolve is an error (FR-005).

## 2. Graph IR

The IR is the contract between expansion, import, materialisation and (later) sim-rs.

**Inputs are the primitive.** A transaction lists the outputs it spends and the outputs it
only reads. Conflicts, orphans and reference contention are never declared; they are
derived from those lists (below).

```yaml
version: 0
wallets: [alice]               # symbolic owners; bound to keys at materialise time
validators:                    # optional; scripts that outputs can be locked to
  <name>: { kind: always_succeeds, budget: { mem: <u64>, steps: <u64> }, size: <u32> }
  <name>: { kind: native, script: <native> }   # native: { sig: <wallet> } | { all: [...] } | { any: [...] }
                                               #   | { after_slot_offset: <i64> } | { before_slot_offset: <i64> }
policies:                      # optional; minting policies
  <name>: { kind: signed_by, wallet: <wallet> }   # native script, wallet signature
sources:
  <name>: { owner: <wallet>, lovelace: <u64> }
txs:
  <name>:
    inputs: [<ref>, ...]               # spent; a set on the ledger, so order is not significant
    reference_inputs: [<ref>, ...]     # read only; optional
    collateral: <ref>                  # required iff an input is locked by a validator
    mint: { <policy>.<asset>: <i64> }  # optional; negative burns
    outputs:
      - to: <wallet> | script:<validator>
        lovelace: <u64> | min | change # exactly one `change` per tx
        tokens: { <policy>.<asset>: <u64> }   # optional
        datum: { bytes: <u32> } | { inline: <cbor-hex> }   # optional
        pad_bytes: <u32>               # optional, inflates tx to a target size
    template: { file: <path>.tx3, tx: <name>, args: { ... }, hash: <blake2b256> }  # optional (story 5)
    validity: { from_slot_offset: <i64>, ttl_slots: <u64> }  # optional, relative to replay start
    labels: [<string>, ...]
    metadata: { <label>: <value> }     # optional, see below
    color: <rrggbb>                    # optional colour tag, metadata label 1022
    cost: { cpu: <share|units>, mem: <share|units> }   # optional script cost, see below
```

Spending an output locked by `script:<v>` uses validator `<v>`'s execution budget for
that input's redeemer, so a batch transaction that spends a pool output and several order
outputs uses each one's validator. Built-in validator kinds (`always_succeeds` with a
target size and budget) are generated by `txflow`; their code hash is fixed per kind and
parameters. A `native` validator needs no redeemer, budget or collateral; its `sig` wallets
sign the spending transaction, and slot offsets are relative to replay start like
`validity`.

**Derived relations** (computed by `txflow`, written to the canonical IR, never hand-edited):

```yaml
derived:
  topo_order: [chains/a1, chains/b1, chains/a2, chains/b2, chains/a3, chains/b3]
  conflict_sets:            # spend/spend: ≥2 txs list the same output in `inputs`
    chains/c1: [chains/a1, chains/b1]
    chains/c2: [chains/a2, chains/b2]
  reference_contention:     # spend/read: one tx spends what another only reads
    pool/p0: { spent_by: [pool/batch1], read_by: [pool/quote3] }
  orphan_on:                # tx → conflict sets among its ancestors; it is invalid if its ancestor loses
    chains/a2: [chains/c1]
  hash: blake2b256:<hex>
```

**Rules**

- Every input, reference input and collateral is a named reference, so the materialiser
  never selects coins (FR-011).
- A transaction may not spend or read an output that one of its own ancestors spends; it
  could never be valid, so it is rejected rather than reported as a conflict.
- An output index has no leading zeros (`t.0`, never `t.00`), so each output has exactly
  one spelling.
- Two `reference_inputs` entries on the same output are not a conflict.
- `topo_order` follows spend and read edges only. It does not place a tx that reads an
  output before the tx that spends it, so when both matter (reference contention) the
  schedule, not `topo_order`, decides which lands first.
- A transaction may belong to several conflict sets (it spends several contested outputs)
  and may be both in a conflict set and orphaned by an ancestor's conflict.
- `change` absorbs the remainder after fees, explicit outputs and minted value; a negative
  remainder, or a token output not covered by inputs plus `mint`, is an error naming the tx.
- Canonical form, used only for hashing: keys sorted, maps sorted by name, `inputs` and
  `reference_inputs` sorted (they are sets), no YAML anchors, integers as integers; the
  emitted IR file need not be in that order.
  The hash covers everything except the `derived` block (computed from the rest),
  including validator definitions and
  each template's `hash` (the blake2b-256 of the `.tx3` file, filled in at expand time), so
  editing a template or a validator changes the IR hash (FR-006).

**Metadata and colour.** `metadata` maps labels (unsigned 64-bit integers) to values in
the plain JSON mapping of `cardano-cli --json-metadata-no-schema`: integers, text, lists
and maps with text keys; text starting with `0x` is a byte string. Expansion checks the
ledger's rules (text and byte strings of at most 64 bytes, integers from -2^63 to
2^64-1, no fractions, booleans or null) plus txflow's own: nesting at most 8 deep, at
most 8 KB encoded per tx, and labels 674 (txflow's attribution message) and 1022
reserved. `color` is written under 1022 as three bytes of RGB, the form
`tx-firehose --color` writes and `mempool-monitor` paints by. Both go on experiment txs
only, never on funding or sweep txs, beside the label 674 message in one auxiliary data
map. Empty `metadata` and a missing `color` are left out of the canonical form, so a
graph without them hashes as it did before they existed.

**Script cost.** `cost` says how much Plutus execution a transaction carries, not which
script runs: the load a node takes on to validate it. `cpu` (CPU steps) and `mem` (memory
units) are each a share of the network's per-transaction limit, `maxTxExecutionUnits`
(`25%`, `12.5%`: above 0, at most 100, at most two decimals, no spaces or leading
zeros), or a whole number of units written as a number.
At least one is given; one left out is kept as low as the script allows. A share keeps
the IR network-free: `cpu: 25%` is a quarter of whatever the target network allows.

Materialise turns a cost into a run of txflow's **burner**, a fixed Plutus V3 script of
204 bytes. It hashes a 64 KiB buffer and counts down, as often as its redeemer says, and
uses the same budget whatever the transaction around it. Its cost is a sum of known
terms, calibrated once per run against the context's cost model and protocol version,
so materialise picks the redeemer that comes as close to the target as possible without
going over (within about 0.01% for CPU targets on Musashi). Each script transaction then:

- spends one extra input, its **fuel**: an output that funding locks at the burner's
  address (no datum) holding the min-UTxO plus this transaction's execution fee, so a
  cost needs no larger sources; the redeemer and its execution units go with it, and
  the min-UTxO part returns in the transaction's change;
- names the run's one **collateral** output, which funding pays to the run address and
  which no transaction spends unless its script fails, which the burner never does;
- pays the script's execution fee on top of the size fee, `ceil(priceMemory · mem +
  priceSteps · steps)`, and carries the script data hash for Plutus V3. Redeemers are
  written as a map, the only form Dijkstra accepts (Conway accepts it too), so both
  encodings share one body and one tx id.

Before the manifest is written, every script run is evaluated with the Plutus evaluator
under the context's cost model; a measured cost that differs from the predicted one is an
error. Some costs no script can reach: on Musashi any Plutus script spends at least
about 160 CPU steps per memory unit, and the burner spans about 240 (counting) to
25,000 (hashing). Below the burner's floor, above the per-transaction limit, or at a
ratio it cannot reach, materialise fails naming the transaction and saying what is
reachable. A missing `cost` is left out of the canonical form.

A script transaction that never lands (the losing side of a conflict, or one orphaned by
it) leaves its fuel at the burner's address: the min-UTxO plus the execution fee it
would have paid, about 1.06 ADA at `cpu: 25%` on Musashi and 2.5 ADA at a full budget.
Anyone can spend it there (the burner succeeds for any redeemer, e.g. `[0, 0, 0]`), so
a third party could also take a fuel output before its transaction is released; that
transaction then fails as spending a missing input. txflow does not sweep fuel yet. The
manifest's `burner` names the address.

## 3. Experiment spec

```yaml
version: 0
experiment: <name>
seed: <u64>
params: { <name>: <integer> }          # referenced as {{ name }} in pattern args
wallets:
  <name>: {}                            # MVP: all wallets bind to one key
metadata: { <label>: <value> }          # optional, on every tx (§2)
color: <rrggbb>                         # optional colour tag on every tx
cost:                                   # optional script cost on every tx (§2)
  cpu: <share|units|expr>               #   `25%`, `2500000000`, `"{{ dose }}%"`
  mem: <share|units|expr>
  select: { label: <label> }            #   optional: only txs with this label
validators: { ... }                     # optional, same schema as §2
policies: { ... }                       # optional, same schema as §2
patterns:
  - id: <instance-name>
    use: <pattern>
    count: <expr>                       # instances to emit, default 1
    with: { <arg>: <expr> }
    metadata: { <label>: <value> }      # on every tx it emits, over the spec's
    color: <rrggbb>                     # over the spec's
    cost: { cpu: ..., mem: ..., select: ... }   # instead of the spec's
txs: { ... }                            # optional explicit IR txs, same schema as §2
sources: { ... }                        # optional explicit sources
schedule: { ... }                       # see §5
expect: [ ... ]                         # see §7
```

A tx's own `metadata` replaces the pattern's or spec's label by label (a whole label,
no deep merge), and its own `color` replaces theirs; a pattern instance's do the same
over the spec's. A `cost` replaces a wider one whole, never field by field: a pattern's
`cost: { mem: 2% }` under a spec's `cost: { cpu: 25% }` gives its txs a memory target
only. `select.label` limits a spec or pattern cost to the txs with that label, so one
side of a conflict can carry the load; the others carry none. A label that no tx has
(no tx the pattern emits, for a pattern's cost) is an error, as in a schedule. Spec and pattern costs may
use params (`"{{ dose }}%"` for whole percent, `"{{ steps }}"` for units); a tx's own
`cost` holds plain values only.

`<expr>` is a number, a `{{ param }}` substitution, or simple arithmetic over params
(`{{ pairs * scale }}`). No conditionals or loops: anything richer belongs in a pattern.

**Scaling is explicit.** `scale` is an ordinary param with no built-in meaning. A spec
scales by referencing it in `count` or in a pattern argument (`users: "{{ 50 * scale }}"`).
Patterns never read params the spec did not pass them, so a value cannot be applied twice.
Scaling `count` gives more independent copies; scaling an argument such as `users` gives
more contention inside one instance.

### Pattern catalogue (MVP)

| Pattern | Emits | Arguments |
|---|---|---|
| `independent` | `n` unrelated single txs | `n`, `ins`, `outs`, `size` |
| `chain` | `t1 → … → tN` | `length`, `ins`, `outs`, `size` |
| `fan_out` | one tx with `width` outputs, each spent by a child | `width` |
| `fan_in` | `width` txs whose outputs one tx spends | `width` |
| `conflicting_chains` | chains `a` and `b` | `length`, `conflict: root \| per_step \| every_k`, `k` |
| `conflict_set` | `k` txs spending one source | `k` |
| `branch_merge` | fan-out whose branches one merge joins again | `width` |

After script support: `order_batch` (`users`, `orders_per_batch`, `batches`, `validator`)
and `contended_state` (`contenders`, `rounds`, `validator`). Both generate `collateral`
sources for every script spend.

## 4. Chain context and manifest

### Chain context (input to materialise)

Materialise performs no network I/O. It reads a chain-context file:

```yaml
network: testnet                 # testnet | mainnet (address network id)
magic: 164                       # network magic; must be 764824073 exactly when mainnet
era: dijkstra                    # txs are encoded in the Dijkstra format (no is_valid)
pparams:                         # or `pparams_file: <path>` to a `cardano-cli query
  min_fee_a: 44                  #   protocol-parameters` JSON (txFeePerByte, txFeeFixed,
  min_fee_b: 155381              #   maxTxSize, utxoCostPerByte are read; the rest ignored)
  max_tx_size: 16384
  coins_per_utxo_byte: 4310
  # Read only when a tx has a `cost`; a pparams_file gives them as cardano-cli
  # writes them (collateralPercentage, executionUnitPrices, maxTxExecutionUnits,
  # costModels.PlutusV3, protocolVersion).
  collateral_percentage: 150
  execution_unit_prices: { price_memory: 0.0577, price_steps: 0.0000721 }
  max_tx_execution_units: { memory: 16500000, steps: 10000000000 }
  cost_models: { plutus_v3: [100788, 420, ...] }
  protocol_version: { major: 12, minor: 0 }
funding:
  signing_key_file: <path>.skey  # or `signing_key_hex`; one payment key spends all offered UTxOs
  change_address: <bech32>       # optional; where the last funding tx returns change
                                 #   (default: the key's enterprise address)
  utxos:                         # offered, in order of preference
    - { utxo: "<txid>#<ix>", lovelace: <u64> }   # ADA only: no native tokens
```

Materialise uses the smallest prefix of `utxos` whose value covers the sources, a fee
reserve of one maximum-size fee per funding transaction, and the min-UTxO change. The rest
stay untouched. A shortfall is reported with the amount needed before anything is built.
Relative paths resolve against the context file's directory.

How the file is produced (a one-off node query, Ogmios, db-sync, or a future net-rs N2C
client) is outside the format. `txflow context` may offer helpers.

### Run key

All sources are paid to a **run key** derived from the funding key, the IR hash and the
seed, never to the funding key's own address. Other tools using the funding key, and other
`txflow` runs, therefore cannot spend an experiment's sources between `fund` and `replay`.
The key is blake2b-256 over a fixed tag, the funding key, the IR hash and the seed.
`txflow run-key` writes it as a `cardano-cli` signing key so leftover outputs at the run
address can be recovered with other tools; it is never written to the manifest.

### Manifest

Written by `txflow materialise`. JSON. Contains no wall-clock data. `txs` is in release
order: funding transactions first (`fund/<k>`), then the experiment in `topo_order`.
Excerpt from the worked example against the demo context:

```json
{
  "version": 0,
  "experiment": "conflicting-chains",
  "ir_hash": "blake2b256:a4acd17c…",
  "run_id": "171f71c864f077a9",
  "seed": 42,
  "era": "dijkstra",
  "tx_format": "conway",
  "network": "testnet",
  "network_magic": 164,
  "pparams": { "min_fee_a": 44, "min_fee_b": 155381, "max_tx_size": 16384, "coins_per_utxo_byte": 4310 },
  "pparams_hash": "blake2b256:56440c94…",
  "funding_address": "addr_test1…",
  "run_address": "addr_test1…",
  "funding_utxos": ["1111…1111#0"],
  "txs": [
    { "index": 0, "name": "fund/0", "kind": "funding", "tx_id": "12b1aaab…", "fee": 176545, "size": 481,
      "inputs": [{ "ref": "1111…1111#0", "utxo": "1111…1111#0" }],
      "outputs": [2000000, 2000000, 2000000, 10000000, 10000000, 973823455],
      "sources": ["chains/c1", "chains/c2", "chains/c3", "chains/wa", "chains/wb"], "cbor_hex": "84a4…" },
    { "index": 3, "name": "chains/a2", "kind": "experiment", "tx_id": "ca515927…", "fee": 169549, "size": 322,
      "inputs": [{ "ref": "chains/a1.0", "utxo": "b1787e7e…#0" }, { "ref": "chains/c2", "utxo": "12b1aaab…#1" }],
      "outputs": [13660902], "labels": ["side-a"],
      "conflict_sets": ["chains/c2"], "orphan_on": ["chains/c1"], "cbor_hex": "84a4…" }
  ]
}
```

- A funding transaction pays the sources in name order, then its change as the last
  output: to the funding key's address, except the last funding transaction, which pays
  `change_address` when one is set (earlier change is spent by the next funding tx,
  which only the funding key signs).
- `run_id` is the first 8 bytes (hex) of blake2b-256 over `ir_hash`, `seed`, the protocol
  parameters used, the funding UTxOs spent (sorted, with their lovelace), the change and
  funding addresses and the network magic, so the same inputs give the same `run_id`
  (FR-012).
- Funding is split into as many funding transactions as `maxTxSize` needs (at most 200
  sources each; the first, which spends every selected offered UTxO, may hold fewer), chained
  so later funding txs spend earlier ones' change. All are built offline with the rest of
  the graph. `funding_utxos` is empty when the IR has no sources.
- Transaction metadata (FR-013) uses label `674` (CIP-20 message), the label `tools/txs`
  already uses, so both tools' transactions can be found on chain and in node traces the
  same way. It holds only short fixed-size strings, well under Cardano's 64-byte limit:
  `{ "msg": ["txflow/1 <origin>", "spec:<8-byte IR hash prefix, hex>", "run:<run_id>#<tx index>"] }`.
  `txflow/1` names the tool and this layout's version; `<origin>` is where the txs were
  built (`cli`, or the site's `SITE_NAME`, e.g. `txflow.fun`). Sweeps carry
  `["txflow/1 <origin>", "sweep", "run:<run_id>"]` and the lane split `["txflow/1 cli", "split"]`.
  The manifest maps `index` back to the symbolic name, so names of any length are safe.
  The tx-firehose colour tag (label 1022) is separate and optional.
- When any tx has a `cost`, funding also pays the collateral and one fuel output per
  script tx, after the IR's sources (named `:collateral` and `<tx>:fuel` in the funding
  tx's `sources`), and the manifest gains:

  ```json
  "burner": { "script_hash": "73827c80…", "address": "addr_test1w…",
              "collateral": "b40a996b…#12", "floor": { "steps": 7576215, "mem": 38164 } },
  ```

  and each script tx gains its collateral and its cost, as asked, as units against the
  context's limit, as measured by the evaluator, and the redeemer that produced it:

  ```json
  "collateral": "b40a996b…#12",
  "cost": { "requested": { "cpu": "25%" }, "target": { "steps": 2500000000 },
            "measured": { "steps": 2499737523, "mem": 160852 },
            "knobs": { "hashes": 36, "bytes": 65344, "loops": 0 } }
  ```

  The manifest's `pparams`, their hash and so `run_id` include the Plutus parameters
  only when a tx has a cost, so a run without one does not depend on them: the same spec
  gives the same txs whether the context's pparams file carries them or not.

## 5. Schedule

Part of the spec, or a separate file passed to `txflow replay`.

```yaml
schedule:
  releases:
    - select: { label: side-a }       # or { names: [a1, a2] } or { pattern: chains }
      target: frankfurt               # a relay of the site's network, or a name in `targets`
      via: n2n                        # n2n | n2c
      at: 0ms                         # offset from replay start
      spacing: 0ms                    # between consecutive selected txs, in topo order
    - select: { label: side-b }
      target: tokyo
      via: n2n
      at: 0ms
  targets:                            # only for nodes outside the site's network
    node1-socket: { socket: "node1/node.socket" }
  options:
    skip_descendants_of_rejected: false   # takes effect only for n2c releases
    observe_for: 120s                     # how long to watch for on-chain inclusion
```

`at` and `spacing` are `0`, `<n>ms` or `<n>s`, at most one hour. Relays come from the
network file (`networks/<id>.json`: id, label, `host:port`, accepted `via`); `txflow check
--network` and the page reject a release whose target is neither a relay nor in `targets`,
or whose `via` the relay does not accept. A transaction matched by several releases is submitted by each. A transaction matched by
none is not submitted (a warning lists them). `trigger:` is reserved for event-based
release (out of scope for now). The schedule has its own canonical hash, recorded in
results next to the IR hash: two runs are comparable only if both match.

## 6. Results

`results.jsonl`, one JSON object per line. `t_ns` is monotonic from replay start;
`run_start` anchors it to wall-clock time and slot.

```json
{"t_ns": 0, "event": "run_start", "run_id": "…", "ir_hash": "…", "schedule_hash": "…", "seed": 42, "network": {"magic": 164, "era": "dijkstra", "pparams_hash": "…"}, "start_utc": "2026-10-12T14:03:11.204Z", "start_slot": 3061391, "txflow": "0.1.0", "targets": {"relay-tokyo": {"node_version": "…"}}}
{"t_ns": 1203400, "event": "offered", "tx": "chains/a1", "tx_id": "…", "target": "relay-tokyo", "via": "n2n"}
{"t_ns": 1350950, "event": "body_requested", "tx": "chains/a1", "tx_id": "…", "target": "relay-tokyo"}
{"t_ns": 1450210, "event": "rejected", "tx": "chains/b1", "tx_id": "…", "target": "node1-socket", "via": "n2c", "reason": "…"}
{"t_ns": 9800000000, "event": "on_chain", "tx": "chains/a1", "tx_id": "…", "slot": 3061401, "block": "rb|eb", "block_hash": "…"}
{"t_ns": 120000000000, "event": "outcome", "tx": "chains/b2", "result": "lost_conflict", "conflict_set": "chains/c2", "also": ["orphaned"]}
{"t_ns": 120000000000, "event": "run_end", "expectations": [{"id": "one_per_conflict", "pass": true}]}
```

What each transport can report:

| Transport | Events |
|---|---|
| N2N TxSubmission | `offered` (tx id announced), `body_requested`. The peer's mempool decision is not sent back, so there is no `accepted` or `rejected`. |
| N2C LocalTxSubmission | `accepted`, or `rejected` with the node's reason |
| Observation (db-sync or node logs) | `on_chain` with slot and RB/EB |

At the end of `observe_for`, every submitted tx gets one `outcome`: `included`,
`lost_conflict` (another member of one of its conflict sets landed), `orphaned` (an
ancestor did not land), `lost_reference` (an output it reads was spent first), or
`not_seen`. A tx can carry more than one cause in `also`.

## 7. Expectations

```yaml
expect:
  - id: one_per_conflict
    each_conflict_set: { on_chain: exactly_one }
  - id: a_side_fast
    select: { label: side-a }
    on_chain_within: 40 slots           # from the tx's own submission, via start_slot
  - id: no_split_block
    each_conflict_set: { same_block: never }
```

## 8. Import (story 4)

`txflow import --db <postgres-url> --address <addr>... --slots <from>..<to> --fidelity shape|values|scripts`
writes a spec containing explicit `txs`, `sources`, `validators`, a `schedule` reproducing
relative arrival times, and, where fitting succeeds, a commented-out equivalent `patterns`
entry. Role assignment: the script address becomes `script:<n>`; each distinct payment
key becomes `user_<n>` in first-seen order; a key that spends three or more script
outputs in one tx is labelled `batcher`.

## Worked example

The P1 experiment: a1→a2→a3 and b1→b2→b3, each aᵢ conflicting with bᵢ.

```yaml
version: 0
experiment: conflicting-chains
seed: 42
wallets: { alice: {} }
patterns:
  - id: chains
    use: conflicting_chains
    with: { length: 3, conflict: per_step }
schedule:
  releases:
    - { select: { label: side-a }, target: node1, via: n2n, at: 0ms }
    - { select: { label: side-b }, target: node2, via: n2n, at: 0ms }
  targets:
    node1: { host: "127.0.0.1:3001" }
    node2: { host: "127.0.0.1:3002" }
expect:
  - { id: one_per_conflict, each_conflict_set: { on_chain: exactly_one } }
```

It expands to:

```yaml
sources:
  chains/wa: { owner: alice, lovelace: 10000000 }
  chains/wb: { owner: alice, lovelace: 10000000 }
  chains/c1: { owner: alice, lovelace: 2000000 }
  chains/c2: { owner: alice, lovelace: 2000000 }
  chains/c3: { owner: alice, lovelace: 2000000 }
txs:
  chains/a1: { inputs: [chains/c1, chains/wa],   outputs: [{ to: alice, lovelace: change }], labels: [side-a] }
```
